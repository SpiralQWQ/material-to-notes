# 总工具 · SOP（给 AI 的强制流程）

本文件是「正规流程约束 AI 不越界」的落点。**可自由发挥的地方写明可发挥；不能省的地方写死，少一步就停。**

> 文中出现的模块名（如 `gates.machine`、`orchestrate.failures`）是简写；实际导入前缀为 `material_to_notes.`（源码在 `src/material_to_notes/`）。

---

## 一、角色：主对话派发，所有 AI 工作由它开的子 agent 承担

```text
主对话派发 ──▶ 执行子 agent ──▶ 审核子 agent ──▶ 通过？──▶ 下一步（仍由主对话派发）
   │                                │
   │                                └─ 不过 ──▶ 打回执行（单步最多 3 次尝试）
   └── 最后做总验收（对着总进度单 + 原始证据，不采信「agent 说过了」；五步见 §七 7.4）
```text
- **主对话**：只做四件事——**派发每一步、在步与步之间交接接口、盯错误预警、决定重试或停下**。不亲自跑零件、不亲自写笔记。
- **执行子 agent（每步一个）**：把这一步跑成；`note` 步由它**亲自按 mre 规范写笔记**，不是 shell 调 mre 再让 mre 去找模型。
- **审核 / 质检 / 评分 / 语义对账子 agent（每步一个，独立）**：拿原始产物独立复核，**不共享执行者的上下文**。
- 全程**串行**，任何一步不过就不进下一步。

### 硬约束（不可违反）

1. **禁止并行**：一次只允许一个子 agent 在跑。**不得并发、不得批处理式同时开多个**。需要提效也不能靠加并发。
2. **判断类工作不用第三方模型**：**派发 / 质检 / 审核 / 评分 / 语义对账 / 写笔记**一律由**主对话开启的子 agent** 完成，**不调 GLM、不调 DeepSeek、不调任何外部 LLM 接口**来做判断类工作。
   - 连带结果：`mre` 的 `executors.yaml` **不需要改**——本流水线不再以 headless 方式走 mre 内部那四个环节，那零件一个字都不用动。
   - 原验收标准里靠 GLM 的条目（GLM 评分、双模型质检、语义对账）**改由审核子 agent 承担**，判定仍为软卡。
   - **例外（用户 2026-10-13 明确）**：**视觉模型不算在禁用范围内**。零件内部的图像理解（m2m 的 `--glm`、dtmd 的 `enrich` 插图融合，走 OCR + GLM 视觉）产出的是**正文素材**，属于**必须保留、且必须可用**的能力，不禁用、不改动。
3. **不采信自报**：判断类结论必须配**可指的证据**（文件、行号、门禁原始输出），主对话只认原始证据。
   - **这条同样适用于审核子 agent**：它报上来的问题，主对话要**逐条到产物里核一遍**再决定是否打回。
     2026-10-13 实测：一次审核报了 5 条，其中 2 条经核实不成立（一条把图 5 的 OCR 判成"完全干净"，
     实际那段公式被拆行；一条拿 `run.log` 里的失败记录推断执行方重试过，而那条记录早于该步、与它无关）。
     审核方不是权威，是**另一个需要被核对的证据源**。
   - **审核方跑偏时，等于没审**：同一天还有一次审核返回的是答非所问的胡话（既没有判定、也没有证据）。
     它**不算通过、也不算不通过**——按"没有可采信的审核结论"处理：要么重派一次，要么由主对话
     用可指证据自己补足。**绝不因为"审核 agent 跑完了"就当成过。**
   - 反过来也成立：**执行方的自述若与事实不符**（如声称"未做任何改写"却做了节选），即使门禁全绿，
     也应当作问题记录在案。
4. **发现属于零件的问题，记下来、别就地改零件**：零件各自是独立仓库，`parts/` 只是按锁表
   拉取的快照，改它等于改一份没人会合并的副本。凡是"零件自己有毛病"的，
   一律去**那个零件自己的仓库**提 issue 或 PR（仓库地址见 `docs/UPSTREAM.md`，
   写清**哪一行、怎么复现、不改会怎样**）；修合并、推送后，把新的 commit 号填进
   `scripts/setup_parts.py` 的锁表，再按 `docs/UPSTREAM.md` §三 的步骤重新验证。
   我们自己这层只做**兜底**。**动零件之前先列出与用户确认。**
   > 历史注记：2026-10-15 到 10-24 之间，这个项目曾把零件复制进 `parts/` 并**就地修过几处**，
   > 那些修补后来都已回灌上游并推送。现在 `parts/` 是拉取产物，**就地修这条路已经没有了**——
   > 这也是升锁表前必须跑端到端的原因（零件一改名、一挪目录、一改规范，流水线不报错，
   > 只会静默产出错东西）。
5. **长任务要分批落盘**（实操教训，2026-10-13）：本环境的子 agent 跑长任务时实测会断——
   两次 `Connection lost mid-response`、两次 `429 Rate limit`。凡是**一次产出很多内容**的任务
   （写一份长笔记、批量补小节），派活时就要写明**分小批做、每批做完立刻落盘**，
   **不要攒到最后一次性写**：攒着写，一断就整份白干。
   失败后的处置：`Connection lost` / `429` 属环境问题，**重派即可**；但**连续 2 次全败就挂起问用户**，
   不得自行切换模型。写盘过的部分不会因中断而丢失，所以分批本身就是最好的保险。


## 二、每一步固定动作（不可省）

1. **开工**：`pipeline init <工作目录>` 建目录 + 写状态（幂等，不覆盖已有）。
   **投料面试**：用户把素材丢进来时，**主对话只问三件**——① 这批素材叫什么（默认用素材自己的名字）
   ② 笔记放哪（默认就地放 `04_笔记/`；也可指定交付目录）③ 笔记给谁看 / 干什么用（默认"教学素材库"）。
   答案写进 `pipeline intake <工作目录> …`，落成 `_元数据/投料单.json`——**答一次就够，之后复用**；
   要改是显式改单子，不是再问一遍。**不答也能跑**：全走默认，且 `run`/`step` 开跑前会打一行说明本次是否用默认。
2. **选路**：`pipeline route <输入>`；**不认识的输入停下问人，不猜**。
3. **派活**：`pipeline assign <工作目录> <步骤>` 出任务单 → 交给一个**执行子 agent**。
   - **派活即留底**：`assign` 会先把该步现有产物拷进 `_state/快照/<步骤>/<时间戳>/`
     （每一步执行前同样会留）。**这是"打回修复只改了几处"能 diff 自证的前提**，
     也是"原件留底绝不覆盖"从输入素材扩展到我们自己产物的落点。`pipeline snapshots <工作目录> <步骤>` 可列。
   - **逐步跑（主路径）**：`pipeline step <工作目录> <步骤>` —— 一次一步，一步一个子 agent，**严格串行**。
   - **重跑**：`--force`（忽略续跑记录强制重跑该步）。改了某一步的**代码**而输入指纹没变时，
     resume 看不出它需要重做，必须显式 `--force`；`pipeline run --force` 同理，重跑整条链。
   - 清洗另有 `--deep-clean`（走 tce 全规则，只适合网页/OCR 噪音素材；保真门禁不豁免它）。
   - `note` 例外：**由子 agent 亲自写笔记**。三步走，顺序不能颠倒：
     ① **写完 → 主对话跑 `pipeline toc <工作目录>`**：篇内目录由**零件自己生成**
     （规范原话"脚本后处理自动生成，AI 无需手写"）。零件 `toc_gen.py --apply` 现在
     **发现已有目录就重建**（2026-10-15 修，见回灌清单 A-5）；**零件工具失败时自动把原文写回**，
     不会把目录删了补不回来。
     ② **再跑 `pipeline gate <工作目录> note`**——由**主对话**跑，
     它现在同时做两件事：通用产物契约（存在/非空/编码）**+ note 专属内容硬卡**
     （`gates/content.py` 判 frontmatter 8 字段 / 一句话总结 / 概述 / 核心知识点 / 专业词汇表 / 自测题 / 元信息，
     并**真正调用** mre 的
     `gate_check.py` 判六件套 / 费曼 / 机械对账 / 膨胀率，**禁 `--score`**）。
     门禁跑不起来（找不到 mre 零件 / 缺脚本 / 缺基准源）**一律判失败**，绝不静默放行；
     只想跑通用契约时用 `--contract-only`。
     **门禁通过时**，它会把 `note` 那一行补进总进度单——笔记由 agent 手写、不走
     `pipeline step`，那条链生成的进度单里本来没有这一行（T58）；门禁通过就是"这一步
     确实成了"的认证点。不通过则一个字都不写。
   - **写笔记的人不要跑 `pipeline step <工作目录> note`**：那条命令会 shell 调 mre
     **重新生成** `04_笔记/<名>.md`，把 agent 手写的产物顶掉（T57）。派活单上已明写这条禁令。
   - `pipeline run` 是**自检 / 冒烟**路径（一次跑完机械步骤、把 note 交出来），不是日常主路径。
4. **机器门禁**：跑 `gates.machine.check`，**看原始输出判定**，不看 agent 转述。
5. **审核**：主对话**另开一个子 agent**，把 `gates.review.render(step)` 交给它；它**只报告、不改产物**，每条给证据，没找到就写「未发现」。**不接任何第三方 LLM 接口。**
6. **放行**：机器门禁过 + 审核无阻断问题 → 进下一步。
7. **记录**：每步一句进度（`report.progress.line`）；写日志（`report.logs.record`，带输入指纹）。

## 三、失败与恢复（写死）

- 单步失败**最多尝试 3 次**（每步独立计数）。
- 3 次仍不过 → **停下**，写「失败交班单」（`orchestrate.failures.write`），四要素齐全：卡在哪步 / 报什么错 / 试过什么 / 产物在哪。
- **跑通即清旧单**：一次不中断地跑完，会清掉上一轮遗留的 `失败单.md`（`orchestrate.failures.clear`）。
  两张单必须同口径——不能出现"失败单说某步挂了、进度单说该步完成"。
- **禁止自行修改任何代码**（包括五个零件的代码）。
- 重跑时：状态里 `status=done` 且**输入指纹未变**的步骤跳过；**输入变了则该步重跑**。
- 状态文件损坏不崩：读不出就当没有状态，从头来。

## 四、可以自由发挥 vs 不能省

| 可自由发挥 | 不能省（写死） |
|---|---|
| 清洗规则细节、笔记风格 | 五步顺序、文件接力落点 |
| 审核时怎么抽查、看哪几处 | 机器门禁必跑、原始证据必看 |
| 被标记项的处置方式（修 / 记 / 问人） | 软卡被标记项**必须浮到总进度单** |
| 工作目录的具体位置（与用户商量） | 原件留底、绝不覆盖 |

## 五、安全与边界

- 不硬编码密钥；密钥走环境变量（`.env`，已 gitignore；仓库只留 `.env.example` 空值模板）。
- **交给零件进程的路径一律绝对**——适配器把 `cwd` 设到零件仓库，相对路径会在子进程里解析到别处（真跑踩过）。
- **上游步骤没在状态里记为完成的产物，一律不用**——那是上一轮遗留，读了会拿陈旧内容且全程不报错（真跑踩过）。
- 产物目录里出现 `.bak` 与 `images_notes/` 属正常留底与插图笔记，**不算上游产物**，接力表按精确模式匹配。
- 路径走 `pathlib`，禁手拼字符串、禁硬编码盘符。
- 产物显式 UTF-8；读入允许 BOM。
- 落盘产物**禁 emoji 装饰**。**例外**：笔记模板里的栏目标记（`📚 概述` / `📑 本篇目录` /
  `🧠 核心知识点` / `📖 专业词汇表` / `❓ 自测题` / `📌 元信息`）是**零件规范定死的形状**，
  门禁按它们认栏目——**照写，别删**（用户 2026-10-15 明确"emoji 可以弄"）。
- 对五个零件的任何改动，**先列清单报用户确认**，确认后才改（例外见 §一 第 4 条）。

## 六、产物与交接

- 工作目录：`00_输入 / 01_取材 / 02_转md / 03_清洗 / 04_笔记 / _state / _logs`。
- 结束产出**总进度单**（每步：执行或跳过 / 产物路径），落盘 `进度单.md`。
- 总进度单必须与磁盘一致：标「完成」的步骤其产物必须存在。

## 七、审核与验收的固定动作（Task-17，2026-10-15 固化）

> 这一节把此前只活在实战里的四件事写成**硬动作**：4 轮审核、证据单四要素、终点一致性、组长验收五步。
> 凡"派活写东西"的步骤（尤其 `note`）一律照此走；少一步就停。

### 7.1 每个 Task 走 4 轮审核（缺一轮不算过）

| 轮 | 问什么 | 不合格的样子 |
|---|---|---|
| ① **完成度** | 该做的**每一件**都做了吗？对着派活单逐条数 | 少做一项却报"已完成" |
| ② **回归影响** | 这一改，**别处**会不会坏？上下游、引用点都看过吗 | 只看眼前文件，没看谁在用它的输出 |
| ③ **隐蔽缺陷** | 有没有**看着对、其实错**的？（空集／边界／编码／单位／路径） | "跑通了"就当对了 |
| ④ **质量设计** | 这是不是**最省**的做法？有没有重复实现、两处事实源 | 复制粘贴出第二份真相 |

- 4 轮**全过**才进下一个 Task；任一轮出问题 → 修好**重走 4 轮**（补一句不算过）。
- 这 4 轮由**主对话自己走**，不能只采信审核子 agent 的结论（§一 第 3 条：审核方也要被核）。
- 连续 **3 轮无进展 → 停下上报**，不许硬耗。

### 7.2 每个 Task 落一张证据单（四要素）

落盘 `temp/fixloop_evidence/round_N.md`（`temp/` 不入库，证据留在本机）：

| 要素 | 写什么 |
|---|---|
| **现象** | 改之前**观察到什么**——原始输出 / 复现命令，别转述 |
| **根因** | 为什么会有这个现象（指到 `文件:行`） |
| **核心修复** | 改了什么（前后对照） |
| **影响面** | 谁受影响；哪些测试 / 产物能证明没坏 |
| （附）**4 轮结论** | 上面 4 轮各判了什么 |

> 证据单是**下一轮复查的账本**：复查时**先查账**（上一轮单据齐不齐），缺单就拒绝认"干净"。

### 7.3 终点一致性（殊途同归必须同果）

通向同一终点的不同路径**逐项比对**：状态文件 / 产物内容（**逐字节**）/ 提示文案 / 总进度单 / 退出码。
任一处不同即 bug。分组与判据见 `docs/穷举测试方案.md` §四（G-A~G-E），
自动化在 `tests/exhaustive/test_endpoints.py`（该文件的 docstring 即分组与判据）。

### 7.4 组长验收五步（主对话自己做，不外包）

1. **查账**：本轮证据单齐不齐？缺 → 标红，**拒绝认"干净"**。
2. **回源核**：审核方报的**每一条**都到产物里核一遍再决定打回——审核方会行号偏移、结论不成立。
3. **跑门禁**：机器门禁 + 穷举回归（`docs/穷举测试方案.md` §七 闭包表）自己跑，**看原始输出**。
4. **终点核对**：跑 G-A~G-E 的一致性对照。
5. **落单**：结论写进证据单（`temp/证据单_*.md`，gitignore）；**没做的显式登记**，不许写"应该没问题"。

### 7.5 ⭐ 为什么 §7 这几步不能省（2026-10-16 两轮实测换来的）

**机器门禁查不出"叙述与源文矛盾"。**门禁只查**数字覆盖率**与**格式形状**（六件套齐不齐、
示范角度够不够）。`runs/doc5` 那份笔记里有一句"源文第 8.1 节没有列某某两项"，
而源文明明列了——**门禁一个字都没报**；写手自己另外三处计数错误，也是靠自己跑
"笔记里的数字 vs 源文的数字"全量比对才发现的。

> **结论：独立审核（§7.3 之外的"回源复核"）不是可选项。**
> 2026-10-15/16 两轮审核（`runs/doc4`、`runs/doc5`）**各自都核出了门禁完全看不到的真问题**。

**同时：审核方的证据也必须逐条核。**`runs/doc5` 那一轮审核报的 4 条里，
**1 条是误报**（它自己的输出把真尖括号转义成了 HTML 实体，于是报"正文残留实体"），
**1 条的引文本身错了一个字、行号也偏了一处**。若直接采信，就会去打回写手改一个不存在的问题。

> 这正是 §一 第 3 条那句"**审核方不是权威，是另一个需要被核对的证据源**"。
> 本轮是它第一次**双向**应验：既核出执行方的真错，也核出审核方的误报。

**核引文要用码点比对，别靠肉眼。**本轮修"引错一个字"时，用
`'核心理点项'` 的码点（`0x6838-0x5fc3-0x7406-0x70b9-0x9879`）逐字比对源文，
一次就对上了；而肉眼与错误的正则各坑过我们一次。

**⚠️ 主对话自己核错过的三种情形（都真实发生过，2026-10-15/16）**——核证据时**别踩这三个**：

1. **正则转义写错 → 误报"干净"**：查"笔记里有没有盘符路径"时写成 `[A-Za-z]:[\\/]`，
   实际要用 `[A-Za-z]:\\`。**结果把 7 处真命中报成"0 处"**。
   教训：**核"有没有"的时候，正则写完先用一个已知含目标的样例自测**；或者干脆**不用正则**
   （按字符逐位扫，见 `runs/doc5` 那轮用的写法）。
2. **`grep` 命中了，却只看了那行的开头就下结论**：查"有没有『第七条』"时，
   `grep -n "第六条\|第七条"` **确实列出了 L439**，但打印时用了 `cut -c1-200`，
   那行开头是"第五条"，于是误判"全文没有第七条"、**把执行方的真问题当作误报驳回了**。
   实际上"第七条"就在同一行更靠后的位置。教训：**命中之后要看全行**；要断言"没有"，
   就**单独搜那个确切的串**，别靠"我看了一眼片段"。
3. **把子 agent 的转述当原文**：写手自报"全文仅剩 2 处 `&lt;table&gt;`"，
   我照着去查 `&lt;` —— 其实那是**它自己的报告把真尖括号转义了**，笔记里压根没有实体。

> 这三条合起来是一句话：**"我核过了"必须落到一个能被别人重跑的命令或一段可指的输出上**，
> 而不是"我看了一眼"。本轮最后一次核对改用**码点逐字比对**，一次就对上了——**可重跑的核法才是核法**。

**⚠️ 第四次（2026-10-16 又栽同一个坑）**：验证脚本里写 `b'\\r\\n'` —— 在源码里那是**字面字符
`\r\n`（四个字符）**，不是回车换行，于是把 CRLF 文件误报成 LF、一度以为写手"说了谎"。
正确的写法是 `bytes([13, 10])`，或者干脆 `raw.count(13)`。

> **同一个根因（在源码里手写转义）今天绊了四次**：正则类 `[\\/]`、`\\[`、grep 后看片段不看全行、
> bytes 字面量。
> **对策很简单**：凡是要"判定有无/相等"的核对，**别在源码里手写转义**——
> 用 `chr(92)` / `bytes([13,10])` 这类**从码点构造**的写法，或者用 `ast`/`codepoint` 逐字比。
> **能被别人重跑、且不依赖我手写转义的核法，才叫核法。**

**⚠️ 第五次（2026-10-17）：工具写完不先拿已知案例验一遍。**
`temp/verify_rebuild.py`（脚本已于 2026-10-24 随 temp 清理移除，不可重跑） 里两处 bug 各坑了一次：`ANGLE_ROW` 漏了 `re.M` → 一处都匹配不到；
正文写的是 `类比` 而我按 `通俗类比` 去数 → 一批假警报。
**教训**：**核对脚本写完，先拿一个"已知答案"的案例跑一遍**——既确认它**该响的时候会响**，
也确认它**不该响的时候不响**。工具本身没验过，它的输出就不是证据。

**⚠️ 第六次（2026-10-17）：`grep -o` 在超长行上静默漏匹配。**
核 doc3-5 那份笔记时（很多行数千字符），`grep -o` 配 `.{45}…{45}` 这类上下文窗口：
`34.429` 报 **3 处**（实际 **8 处**）、`三步走` 报 **0 处**（实际 **1 处**）。
我据此**判断"审核方引的行号和原文对不上"**，随后用 `Read` 直接读那几行，
**发现审核方是对的、我错怪了它**。
**教训**：在这个项目的笔记文件（超长行）上，"**有没有 / 在几处**"**只认 `grep -c` 计数模式与直接读行**；
`grep -o` + 上下文窗口的输出**不能当证据**。（第五、六次是同一个病根。）

### 7.6 可读性实测的固定题面（2026-10-17 固化）+ T102 的裁定

**做法**：把笔记**单独**交给一个**没看过源文**的 AI，**禁读原文**（禁令清单要它自己在报告里列出来，
能翻到原文就分不清"是笔记讲清楚了"还是"它自己补的"）。这个做法已在 10 份笔记上跑过 6 轮，
**每一轮都抓出门禁与回源复核都看不见的东西**——所以它是 §7 的**第三种检查**，不是可选项。

**题面（8 问 + 1 个附加，少一问不算跑完）**：

| # | 问 |
|---|---|
| 0 | 先说边界（我按禁令没做的事） |
| 1 | 这是什么材料？干什么用的？ |
| 2 | 核心内容：只让记 5 件事，是哪 5 件？ |
| 3 | 源文本身有什么问题或缺口？（笔记提到的地方，给行号） |
| 4 | 够不够讲给别人听？能讲到什么程度、在哪里讲不下去？ |
| 5 | 结构顺不顺？有没有让读者迷路的地方？ |
| 6 | **哪里看不懂？（必须给行号，不许客气）** |
| 7 | 哪里在凑字数？（**跨知识点、跨栏目**的重复 + 无信息量的段；同一知识点内六件套各说一次不算） |
| 8 | 本轮实测（最重要）：(a) **动手复述一遍**，分"能复述/复算"与"只能靠猜/复现不了"两栏；(b) 「示范角度」够不够自己展开 |
| 9 | **附加：笔记自称的数目 vs 它实际列出的条数** ← 见下 |

**⭐ T102 的裁定：不给门禁加这条检查，改成固定问第 9 问。**
原本打算给门禁加一条"自称数目 vs 实列条数"的正则检查。**先做了标定扫描**（`temp/_count_claim_scan.py`），
结果把这条路否掉了：

- 第一版（自称的数 + 紧接着的圆圈序号）：九份笔记报 **16 处候选**，逐处读下来**几乎全是误配**
  （"七条假设可分三类"、"五条风险，每条两段式"）——**不可用**；
- 第二版（自称的数 vs 文档里**可数的对象**：元信息条目数 / 知识点数 / 目录条目数 / 词汇表行数）：
  九份笔记报 **0 处不一致**。**而同一轮的可读性实测在 doc3-5 上抓出真不一致 3 处**
  （"三步走"实列四步、"三城"实列四个地名、"广州 4 次"vs 正文 5 个）。
- **判据是语义的**（自称的那个词与它旁边列的清单**是不是一回事**），正则做不出来；
  让"没看过原文的人自己数一遍"反而准。

> 所以：**这条不进机器门禁**，**固化成第 9 问**。第 9 问第一次跑就报出 3 处
> （其中 2 处我核为真、1 处是源文自身矛盾且笔记已登记）。
> **存量结论**：这个"撤回"本身就是标定的产出——**没有标定就加进去，会得到一条 16 处误报、真问题 0 命中的假门禁**。
