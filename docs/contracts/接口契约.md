# 接口契约（实测登记）

> 这份文件回答一个问题：**每一步真正跑出去的是什么命令、产物落在哪。**
> 依据是运行日志 `_logs/run.log` 里记下的 **argv**（`report/logs.py` 自 `3f04aef` 起记录），
> **不是**适配器代码"它说它会这么拼"。这条区别是有代价换来的：真跑里 `RELAY` 一份递归一份平铺
> 才对不上、相对路径被交给子进程、清洗悄悄吃掉结构，全都是 mock 全绿而接口不对。

## 一之二、零件从哪来（2026-10-15 契约变更：就地调用 → 库内自带）

五个零件的**代码副本**现在住在 `parts/`（用户批准的架构变更，见 `docs/架构与目录契约.md` 第十节）。
查找顺序写在一个地方 —— `contract/runner.part_tool(env_key, part, env)`：

1. **环境变量优先**（`WKC_DIR` / `DTMD_DIR` / `M2M_DIR` / `TCE_DIR` / `MRE_DIR`）——
   单元测试和「临时换一份零件跑」用这条路；
2. 否则用**库内 `parts/<零件名>/`**（`PIPELINE_PARTS_DIR` 可整体改根目录，测试用）。

所以**全新克隆、`.env` 里一个零件路径都不写，也能跑**。实测（摘掉全部路径后）：五步全部解析到库内副本，
`pipeline gate runs/doc2 note` 仍 **exit=0**。

`parts/<名>/UPSTREAM.md` 记着来源仓库、复制时的提交号、版本；**权威源始终是远端仓库**，
这里只是快照，**代码不在此修改**（零件问题记 `docs/回灌清单.md`）。



每一步只按这张表去上一棒取文件，**不猜路径**。模式是刻意收窄的：`enrich` 会写
`images_notes/*.md`、并把 `full.md` 备份成 `*.md.bak`，宽泛的 `*.md` 会把这两样误当成上游产物。

| 步骤 | 从哪读 | 取哪些 | 上游必须已记录完成（producers） |
|---|---|---|---|
| clean | `02_转md/` | `**/*_mineru/full.md`、`**/*_clean.md` | document 或 media |
| note | `03_清洗/` | `**/*.txt` | clean |

**一个工作目录可以装多份素材**，所以这些模式常一次匹配到多份：

- **产物命名**：**中间产物按源名**（`03_清洗/<源名>.txt`，源名天然唯一，改名不动它）；
  **交付物按显示名**（`04_笔记/<显示名>.md`，显示名来自投料单）。两边**经投料单反向映射配对**，
  不假设同名。混用会让改名留下一份孤儿、把一份素材变成两份。
- **逐份循环**：`default_executors` 的 clean / note 逐份执行，任一份失败即整步失败。
- **撞名只可能发生在交付物上**（源名撞不了）：两份素材解析成同一个笔记名 → 停下问用户。

`relay_guard` 拦三种情况，一律**停下问用户**而不是悄悄往下走：
1. 上游一个文件都没有；
2. **两份素材会写成同一个交付物名**；
3. 上游文件是**上一轮失败遗留**的（`producers` 没记录完成）——这种最阴：不报错，但喂给下一步的是陈旧内容。

## 二之二、投料单（`_元数据/投料单.json`）

初始化时问的三件，答一次即长期有效：受众（默认"教学素材库"）、交付目录（默认就地）、改名表（默认用源名）。
写它用 `pipeline intake <工作目录> [--audience …] [--deliver-dir …] [--name <素材名>=<名字>]`；
不答也能跑，`run`/`step` 第一行会明说本次是否全用默认。交付用 `pipeline deliver <工作目录>`
（拷贝而非移动；没指定目录时就地并说明）。

## 三、实测记录

### 3.1 clean（清洗）

**实测命令**（取自 `runs/doc1/_logs/run.log`，路径已用占位符替换）：

```
<python> -m cleaner.clean_md <工作目录>/02_转md/<名>_mineru/full.md \
         --output <工作目录>/03_清洗/full.txt --watermark-only
```

- 工作目录：**库内 `parts/text-cleaning-engine/`**（2026-10-15 起；`$TCE_DIR` 降为可选覆盖，见第一节之二）
- 子进程 cwd：tce 仓库根（否则 `-m cleaner.clean_md` 解析不到）
- 环境：`tool_env()` 把 `<零件仓库>` 与 `<零件仓库>/src` 都压进 `PYTHONPATH`（src 布局的零件靠这个才导入得到），
  并**强制 `PYTHONIOENCODING=utf-8`**（否则 Windows 老代码页下 mre 门禁打印 ✅ 会 UnicodeEncodeError 崩掉、误判门禁坏了）
- **路径参数一律绝对**（`R.abspath()`）：子进程 cwd 在零件仓库，相对路径会被解析到错误目录

**两种模式**（默认是保守的那一个）：

| 模式 | 命令差异 | 适用素材 | 实测后果 |
|---|---|---|---|
| watermark（默认） | 带 `--watermark-only` | 文档线/媒体线已排好版的 markdown | 五类标记 100% 保住 |
| deep（`--deep-clean`） | 不带该参数 | 网页/OCR 噪音素材 | 网关档把 1118 行压成 1 行、表格清零；plain 档公式清零 |

**产物**：`03_清洗/{源文件词干}.txt`（清洗后正文）；该步统计落 `_元数据/{源文件词干}.json`（tce 统计 + 门禁损失记录）。
统计里**不含** `cleaned_text`（tce 会把全文回显，照抄等于把文档存两遍）；有结构损失时多一个 `structure_lost` 字段。

**保真门禁**（`contract/validate.structure_loss`）：行数 / 标题 / 公式 `$$` / 表格 `<td` / 代码围栏五类标记，
上游存在而下游留存 < 90% 即判本步失败，`--deep-clean` **不豁免**。

### 3.2 document（文档转md）

**一个步骤跑三条（普通文档）或四条命令（切片书）**。普通文档实测取自 `runs/probe_doc/_logs/run.log`，
merge 那条取自一本 210 页真书 `runs/book1/_logs/run.log`（占位符替换后）：

```
<python> -m dtmd plan <工作目录>/00_输入
<python> -m dtmd convert --mode cloud 1
<python> -m dtmd merge <工作目录>/02_转md/<名>_mineru        # 仅当确有切片目录
<python> <仓库>/scripts/enrich_subset.py <工作目录>/02_转md/<名>_mineru
```

| 阶段 | 做什么 | 备注 |
|---|---|---|
| plan | 扫 `00_输入` 的文档，出转换计划 | 计划**不在工作目录里**，见下面那条约束 |
| convert | 逐天转换（`1` 是 `DayN`，多天就循环） | 真正的 MinerU 云端消耗点 |
| merge | 把 `p{start}-{end}/` 切片按页序拼回根目录的 `full.md` | **只对切片书调用**，见下 |
| enrich | 只对**被 full.md 引用的图**做 OCR + GLM 视觉，内嵌回 `full.md` | 由 `scripts/enrich_subset.py` 驱动；可用 `--no-enrich` 跳过 |

- 子进程 cwd：dtmd 仓库根；环境额外注入 `DTM_OUTPUT_ROOT=<工作目录>/02_转md`
- 落点：`02_转md/<名>_mineru/` 下的 `full.md`、`images/`、`images_notes/`、`layout.json`、
  `<hash>_content_list.json`、`<hash>_model.json`、`<hash>_origin.pdf`，外加我们自留的 `full.md.bak`
- **`enrich` 会就地覆盖 `full.md`** → 我们在 enrich **之前**先把原版另存为 `full.md.bak`（只留第一份快照），
  满足"原件留底绝不覆盖"
- **切片书的产物布局**：`<名>_mineru/p1-199/full.md`、`p200-210/full.md`…**切片原样保留**，
  合并后的完整 `full.md` 落在 `<名>_mineru/` 根目录（实测：210 页的书切成 199 + 11 两块，目录名**不补零**）

**三条实测出来的约束**（不是设计意图，是量出来的）：

1. **`merge` 只对切片书调用**：`dtmd merge` 在无事可做时退出码是 **1**（"无事发生也提示用户"），
   无条件调用会把每一份普通文档都弄挂。我们只在目录里确有 `p{start}-{end}/full.md` 时才调。
2. **接力契约只认合并后的那一份**：切片原样保留意味着 `**/full.md` 会一次捞到 3 份
   （根 + 两片），下游守卫会拦停。契约写的是 `**/*_mineru/full.md`。
   注意 `contract/steps.py` 的 `produces` **保持宽松**（`**/full.md`）——它每个阶段都校验，
   而切片书在 merge 之前根目录本就没有 `full.md`。分工：`produces` 宽松、`RELAY` 收窄。
3. **计划文件是跨工作目录共享的**：dtmd 把 `plan.json` 写在自己的 `_data/` 里（不在我们的工作目录），
   后一次跑会覆盖前一次。我们的 `run()` 是"先 plan、再读天数"，串行下没问题；
   但**两个工作目录并发跑同一条线会互相踩**，并发前必须先解决（见 T48）。

**我们的 `--force` 到不了 MinerU**：dtmd 自带"已转跳过"（`cloud.py:178`），只有传 **它自己的**
`--force` 才会重转并覆盖。所以 `pipeline step … document --force` 只会让**我们的**续跑逻辑重跑，
**不会**重新消耗 MinerU 额度（实测：重跑三条命令 1 秒返回，产物时间戳不变）。反过来，真想重转必须走 dtmd 的开关。

**成本**：MinerU 云端按页计（每日约 5000 个文件、前 1000 页最高优先级、单文件 200 页上限，
超额降级排队不封死；HTML 有独立配额）；`enrich` 走智谱 `glm-4.6v-flashx`（**免费档**，仅限流重试）；
OCR 是本地 RapidOCR。额度表述以 dtmd README 为准。

## 四、note（写笔记）· 接口形状


**不调 mre CLI。** 按 SOP §一，写笔记是 agent 的活，不是 headless 子进程的活：

- 执行者：主对话开启的**执行子 agent**（一次一个，严格串行）
- 输入：`03_清洗/**/*.txt`（由 `relay_sources` 给出，绝对路径）
- 产物：**每份素材一个** `04_笔记/<显示名>.md`；显示名来自投料单，默认＝源名
- 门禁：由**主对话**跑 `pipeline gate <工作目录> note`。它做三件事——
  ① 通用产物契约（存在/非空/编码）② `gates/content.py` 判 frontmatter / 篇内目录 / 词汇表 / 元信息
  ③ **真正调用** mre 的 `scripts/gate_check.py <该份笔记> --src <它自己那份原文>` 判六件套 / 费曼 /
  机械对账 / 丰富度（**禁用 `--score`**）。每份笔记都跑，`--src` 按**名字经投料单反向映射**配对
- `04_笔记/` 里出现对不上任何素材的 `.md`（改名留下的孤儿）→ **判失败并点名**
- 语义对账与幻觉：由**另一个独立审核子 agent** 按 `pipeline checklist note` 判

## 五、维护规则

1. 新增或改动任一适配器的命令拼装，**必须**重跑一次真跑并核对该步的 argv 与落点，再更新本文件。
2. 本文件与 `contract/steps.py` 的 `produces`、`orchestrate/pipeline.py` 的 `RELAY` 三者是同一份事实的三种表达；
   改一处就要同步另两处，否则又会回到"mock 全绿、接口不对"。
3. 本文件**不得出现绝对路径**（`scripts/privacy_check.py` 会拦）。
