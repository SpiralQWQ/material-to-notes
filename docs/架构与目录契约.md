## 一、定位：这东西到底是什么

`material-to-notes` 是一层**编排层**，自身不含任何"解析 / 转写 / 清洗 / 重写"能力——那些能力全在五个零件里。

它做四件事：

1. 定义五个零件之间怎么交接（**接口契约**）。
2. 把每一步**串起来跑**（选路 → 派发 → 执行 → 审核 → 放行 → 续跑）。
3. 把每一步的**验收标准**落成可执行检查。
4. 产出**总进度单 / 失败单 / 日志**。

五个零件保持独立，本工具**只通过"文件接力 + 命令行调用"使用它们**；对零件的任何改动，先列清单报你确认（见需求清单第二节）。

## 二、总架构（分层）

```text
                       ┌──────────────────────────┐
      输入（链接/文件）  │  编排层 orchestrate       │
   ───────────────────▶│  选路 / 派发 / 审核 / 放行 │
                       │  / 断点续跑 / 失败处理     │
                       └───────┬──────────┬───────┘
                               │          │
                 ┌─────────────▼──┐   ┌───▼────────────┐
                 │ 执行层 steps   │   │ 门禁层 gates    │
                 │ 五个零件的适配 │   │ 验收标准落地    │
                 └───────┬────────┘   └───┬────────────┘
                         │                │
                 ┌───────▼────────────────▼───────┐
                 │ 接口层 contract（单一事实源）    │
                 │ 步骤定义 / 工作目录布局 / 校验   │
                 └────────────────────────────────┘

                 记录层 report：总进度单 / 失败单 / 日志
                 入口   cli  ：命令行入口
```text
六块职责，互不重叠：

| 目录 | 单一职责 | 不许干的事 |
|---|---|---|
| `contract/` | 定义"棒"长什么样：五个步骤的输入/输出/落点、工作目录布局、产物校验 | 不许含任何调用零件的代码 |
| `steps/` | 把五个零件各包一个**薄适配器**（怎么调、传什么参数） | 不许含流程控制（谁先谁后） |
| `orchestrate/` | 串流程：选路、派发、审核、放行、断点续跑、失败计数 | 不许直接拼零件命令行（走 `steps/`） |
| `gates/` | 验收标准：机器门禁 + 给审核 agent 的检查单 | 不许改产物 |
| `report/` | 总进度单、失败单、日志 | 不许判对错 |
| `cli/` | 命令行入口 | 不许含业务逻辑 |

## 三、什么写进脚本，什么写进 SOP（关键设计决定）

这条决定整个项目的形态。原则：**机器能判的写脚本，需要判断的写流程文档。**

- **写进脚本**（确定性、可自动验证）：调零件、建工作目录、跑门禁、断点续跑、重试计数、生成进度单。
- **写进 SOP 文档**（`docs/SOP.md`，需要 AI 判断）：这一步该不该跑、路线怎么选、审核 agent 怎么派、被标记项怎么处置、什么时候停下问人。
- **SOP 就是"正规流程约束 AI 不要越界"的落点**：AI 能发挥的地方写清"可以自由发挥"，不能省的地方写死"必须做、少一步就停"。

## 四、工作目录布局（"统一"的落点）

每次运行一个**工作目录**（用户与 AI 一起定位置，默认在工作目录下）。所有产物落在这里，绝不污染源文件和零件仓库。
**一个工作目录装多份素材**，所以任何产物都不许按"步骤"命名——两份论文会都想叫 `full.txt`。产物按**素材**命名，机器可读的东西一律进 `_元数据/`，于是交付目录里只有交付物：

```text
<工作目录>/
├── 00_输入/      # 拷进来的原件 / 链接清单（原件留底，绝不覆盖）
├── 01_取材/      # wkc 产物
├── 02_转md/      # dtmd 或 m2m 产物（<名>_mineru/ 或 <名>_clean.md）
├── 03_清洗/      # tce 产物 <名>.txt（另存，不覆盖 02）
├── 04_笔记/      # 最终交付 <名>.md —— 这一格只有笔记
├── _元数据/      # 投料单.json + 每份素材一份 <名>.json（来源/时间/各步产物/统计）
├── _state/       # 断点状态、锁（原子写）；快照/ 放各步产物的历史版本
├── _logs/        # 日志
├── 进度单.md      # 总进度单（结束生成）
└── 失败单.md      # 失败交班单（有失败才生成）
```text
**投料单**（`_元数据/投料单.json`）是初始化时问出来的三件事，答一次即长期有效：
受众（默认"教学素材库"）、交付目录（默认就地）、改名表（默认用素材自己的名字）。
不答也能跑，`pipeline run/step` 开跑前会打一行说明本次是否全用默认——**默认不可静默**。

编号前缀固定顺序，`_` 前缀的目录是系统用的。这就是"统一输出"的落地方式——不改零件默认行为，只让零件把产物写到指定位置。

## 五、接口契约（五个插头）

| 步骤 | 吃什么 | 吐什么 | 由谁调 |
|---|---|---|---|
| 取材 | 词汇 / 链接 | 原始文件 + meta.json | `steps/fetch.py` → wkc |
| 转md（文档） | PDF/Word/PPT/HTML | `02_转md/<名>_mineru/full.md` + `images/` | `steps/document.py` → dtmd（plan → convert → **merge** → enrich）|
| 转md（媒体） | 视频/音频/图集 | `{名}_clean.md` | `steps/media.py` → m2m |
| 清洗 | 上一步的 md | `03_清洗/<名>.txt`（统计进 `_元数据/<名>.json`） | `steps/clean.py` → tce（默认 `--watermark-only`，`--deep-clean` 走全规则）|
| 写笔记 | 清洗后 md | `04_笔记/<名>.md` | 由**执行子 agent 亲写**，不调 mre CLI |

真实参数与落点在执行阶段逐条定，写死在 `contract/steps.py`（单一事实源）。**下一棒只按契约取文件，不猜路径。**

清洗这一步还多一道**保真门禁**（`contract/validate.structure_loss`）：行数 / 标题 / 公式 `$$` / 表格 `<td` / 代码围栏五类标记，任何一类在上游存在而清洗后留存低于 90%，本步判失败，并把掉了哪几类写进 `_元数据/<名>.json` 的 `structure_lost` 字段（**不在 `03_清洗/` 里**——交付目录只放交付物）。`--deep-clean` **不豁免**——选了全规则不等于授权丢内容。理由见第十节 2026-10-13 那条变更记录：工具退出码 0 却把内容吃掉，比崩溃更危险，因为损失看不见。

## 六、三个角色与串行流程

```text
对每一步：  主对话派发 ──▶ 执行 agent ──▶ 审核 agent ──▶ 通过？──▶ 下一步
   ▲                          │              │
   │                          │              └─ 不过 ──▶ 打回执行（单步≤3次）
   │                          └─ 报「做完+产物在哪+遇到的问题」
   └──────── 主对话最后做总验收（对着总进度单 + 原始证据，不采信「agent 说过了」）
```text
- 审核 agent **不共享执行者的上下文**，只看原始产物。
- 机器能判的（门禁脚本、文件存在、计数），直接看**脚本原始输出**。

### 依赖方向（单向，禁反向）

```text
cli  ──▶  orchestrate  ──▶  { steps, gates, report }  ──▶  contract
```text
- `contract/` 谁也不依赖，被所有人依赖。
- `steps/ gates/ report/` 之间**互不依赖**。
- `orchestrate/` 是唯一知道"谁先谁后"的地方。
- 反向 import 一律禁止（下一步可用工具强制检查）。

### 目录治理禁止项（Hard Rules）

- 禁建 `py/`、`scripts_by_type/` 这类按类型/后缀命名的顶层目录。
- 禁业务逻辑散落进通用工具文件（本项目不设 `utils/`，需要共享就放 `contract/`）。
- 禁跨层直接 import 内部文件（先经 `__init__.py` 暴露）。
- 禁目录嵌套超 3 层。
- 禁把测试、配置、部署文件混进源码目录。
- 禁真实 `.env` 入库（只入 `.env.example`）。

## 八、命名与其它约定

- 代码全英文（变量/函数/注释/输出），面向用户的文案走中文文档。
- 落盘产物禁 emoji 装饰（Windows 终端易乱码）。
- 路径一律 `pathlib` / `os.path.join`，禁手拼字符串，禁硬编码盘符。
- 所有产物显式 UTF-8；读入允许 BOM。

## 九、明确不做

- 不重构五个零件；不复制它们的代码进本仓（只调用）。
- 不做图形界面。
- 不强行统一零件的默认输出形状（用工作目录 + 参数引到指定位置）。
- 本轮不上 PyPI。

  同一份代码存在两份权威副本，上游改了副本忘了同步，两边行为**静默分叉**；
  而且别人打开仓库看到 5 份 LICENSE、5 份 README，第一反应是"这是聚合站还是项目"。
